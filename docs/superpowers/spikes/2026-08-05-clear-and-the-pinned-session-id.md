# What `/clear` does to a pinned session id

**`/clear` forks the session: Claude Code mints a new id, opens a new
`<new-id>.jsonl`, and never writes to the pinned `<launch-id>.jsonl` again — so a
deck tile reading the pinned filename keeps its pre-`/clear` name for the rest of
the session's life.**

Run 2026-08-08 on the development machine, Claude Code **2.1.224**, macOS
(Darwin 25.5.0). Task 1 of #154 (#155). Everything below is raw output; the
reading is at the end, and no code in this branch was changed because of it.

## The experiment

## Two things found on the way

### The launch id survives inside the new file — but not as a key

The post-`/clear` transcript's assistant records carry `session_id` (snake_case)
holding the **launch** id, while every line's `sessionId` (camelCase) holds the
new one:

```
$ grep -oh '"session_id":"[^"]*"' *.jsonl | sort | uniq -c
   4 "session_id":"6bc4c0f3-50a9-4edf-b59f-6a7cee539fec"
$ grep -oh '"sessionId":"[^"]*"' *.jsonl | sort | uniq -c
  16 "sessionId":"6bc4c0f3-50a9-4edf-b59f-6a7cee539fec"
  16 "sessionId":"6e0347f3-5ed4-41bc-be96-d314586203a8"
```

That reads like a ready-made resolution key — and across the whole corpus it is
not one. Scanning every transcript on this machine (`corpus-check.py`, below):

```
transcripts scanned:                  594
carrying a `session_id` field:         53
whose session_id != its filename:       7
```

Four of those seven carry **two** distinct `session_id` values in one file, and
one carries a single id that is neither its filename nor anything else in its
directory. So `session_id` is a hint about provenance, not an identity: only 9%
of transcripts have it at all (it looks version-dependent), and where it exists
it is not single-valued. A resolver keyed on it would attach the wrong
transcript to a tile some of the time, silently.

### A transcript does not exist for the first half-minute

The process registered itself at 02:16:42 and the file first appeared at
02:17:17 — **35 seconds** with no `<uuid>.jsonl` on disk at all, and then it
appeared at 102,002 bytes in one step. This is the cold-start observation the
spec could not explain: for the first half-minute of a session `find_transcript`
returns `None`, so the tile reports zero tokens and keeps its placeholder name.
That is not a fault and needs no fix — but it is why a brand-new tile looks inert
for longer than the five-second tick suggests.

The title itself is fast once the file exists: 1 second after it in the first
conversation (02:17:17 → 02:17:18), and 1 second in the second (02:18:09 →
02:18:10). The wait is for the file, not for the title.

## What this means for the deck, and what it does not

**Nothing in tasks 2–13 changes, and nothing in them is wrong.** Everything
built on the pinned filename keeps working exactly as designed for a session
that is never cleared, which is the common case. `/clear` is the exception, and
its cost is bounded: the tile keeps the name the conversation started with and
the token count freezes at the pre-`/clear` total. Both are wrong in the same
way and neither is destructive.

But the failure is the ugly kind — **it looks correct**. A tile reading
`Различия между HTTP и HTTPS` while the conversation is three topics further on
is worse than a tile reading `session · relay`, because nothing signals staleness.

**Since this was written, the hook-payload route below was taken and the name
and the token count are fixed in the same branch** (`transcripts.rs`, and
`current_transcript` in `commands.rs`). What is left of the finding is #199: the
`--resume` path still uses the launch id, so restart and auto-restore still
bring back the pre-`/clear` conversation. The rest of this section is the
reasoning that led there, kept as written.

### Which task would change

`session_snapshots` (#157, `src-tauri/src/commands.rs`) — specifically
`find_transcript`, which today trusts the filename. Nothing on the frontend
would move: `TileNames` has exactly one slot for an automatic title, so where
that slot's value comes from is invisible to the resolver, to persistence and to
the editor. That is the property worth having, and this spike does not spend it.

### Claude Code already hands us the answer, on a channel this app owns

Found after the run above, and it supersedes everything in the next section.
**Every hook payload carries `transcript_path`.** Not the id to guess a filename
from — the path itself. Measured by pointing every hook at a script that does
nothing but `cat` its stdin into a log:

```
$ cat ~/clear-spike/… claude --settings '<hooks that dump stdin>' -p "Скажи только слово: готово"
--- SessionStart
   session_id        'f1eaf292-1932-4152-8e6c-d179b9495c56'
   transcript_path   '/Users/…/.claude/projects/-Users-…-clear-spike/f1eaf292-….jsonl'
   cwd               '/Users/evgenykharetski/clear-spike'
   hook_event_name   'SessionStart'
   source            'startup'
--- UserPromptSubmit
   session_id        'f1eaf292-…'      transcript_path  '/Users/…/f1eaf292-….jsonl'
   prompt_id         'e83ec419-…'      prompt           'Скажи только слово: готово'
--- Stop
   session_id        'f1eaf292-…'      transcript_path  '/Users/…/f1eaf292-….jsonl'
   last_assistant_message 'готово'     stop_hook_active False
```

This app already subscribes to `SessionStart`, `UserPromptSubmit`, `Stop` and
`SessionEnd` (`src-tauri/src/hooks.rs:8`), the reporter already reads the hook's
stdin under a 300 ms timeout, and already pulls one field out of it —
`notification_type` (`src-tauri/src/bin/cowork_report.rs:26`). It throws the rest
away. The reporter is invoked with **this app's** session id in argv, so the
binding "tile → its current transcript" is exact, and depends on no filename, no
inner `session_id`, and nothing under `~/.claude/sessions/`.

After a `/clear` the deck therefore does not need to detect anything: the first
`UserPromptSubmit` of the cleared conversation — which is the whole reason
someone clears — carries the new path.

**Not measured:** whether `SessionStart` fires again on `/clear` with
`source: "clear"`. It stopped mattering: any following hook carries the path
regardless, so the fix does not rest on that answer.

This also makes the shape smaller than either candidate below: two more fields
out of a payload already being read, carried on a socket already open, with
`find_transcript` left as the fallback until the first hook of a restored tile
arrives.

One trap for whoever writes it: `extract_field` in the reporter is a naive
flat-JSON scanner that takes the **first** occurrence of a key. `transcript_path`
is the second field of every payload and `last_assistant_message` comes much
later, so field order saves it — which is exactly the kind of thing that wants a
test, or a move to `serde_json`.

### The two candidate fixes considered before that, smallest first

1. **Ask the live process.** The app spawns `claude` itself, so
   `portable_pty`'s `child.process_id()` gives the pid, and
   `~/.claude/sessions/<pid>.json` names the session's **current** id — it
   followed the fork within the same second above. Small, exact, and no
   guessing. Two limits: the record vanishes when the process exits, and a
   **restored** tile has no live process of its own until it is restarted, so it
   would fall back to the pinned filename and stay stale after a `/clear` in a
   previous run. It also leans on an undocumented file, in a directory this app
   does not otherwise read.

2. **Take the title off the PTY** — filed as #196. Claude Code emits it live as
   `ESC]0;<title>BEL` and the deck already receives those bytes; xterm parses
   OSC 0/2 already. This sidesteps the id question entirely for a live tile,
   with the transcript read left as the source for a restored one. Larger, and
   it makes the name depend on whatever the running program printed, which wants
   the same sanitising the Rust side already does.

**Not recommended: resolving by `session_id`.** It is the fix the task
anticipated, and the corpus above is the reason not to: 9% coverage and not
single-valued.

**Also considered and rejected: intercepting `/clear` in the input stream and
relaunching the session.** Detection would be unreliable — slash-command
autocompletion, a paste, arrow-key history, broadcast mode, and the word
appearing inside an ordinary prompt all defeat it, and modelling the prompt
buffer is precisely what the deck avoids by keeping the PTY raw. It is also
destructive for an operation that is meant to be instant: relaunching means
killing the process, losing the scrollback and waiting seconds.

The hook payload makes all of this unnecessary, and it is what the follow-up
records. The token count is forked by exactly the same mechanism — whoever takes
it should decide whether tokens follow the name or stay on the launch
transcript — and so is `--resume`, which is the part that actually loses work.

## The scripts

`clear-spike-watch.py` — polls the slug directory once a second, prints on
change, and reports what `~/.claude/sessions/*.json` says the current id is:

```python
slug = re.sub(r"[^A-Za-z0-9]", "-", os.path.abspath(project))
watch_dir = os.path.join(home, ".claude/projects", slug)
TITLE = re.compile(rb'"(aiTitle|customTitle)":"((?:[^"\\]|\\.)*)"')
# for each *.jsonl: len(data), len(titles), sorted(set(titles)) — printed when it changes
# for each ~/.claude/sessions/*.json whose cwd is the project: its sessionId
```

`corpus-check.py` — the disagreement count above:

```python
pat = re.compile(rb'"session_id":"([0-9a-f-]{36})"')
ids = {m.group(1).decode() for m in pat.finditer(open(path, "rb").read())}
if ids and ids != {name[:-len(".jsonl")]}:
    mismatched += 1
```

Both are throwaway; neither is committed, because neither is something this
repository runs.
