# cowork-deck — «GitHub-аккаунт на воркспейс» — Design Spec

**Дата:** 2026-07-27
**Ветка:** `worktree-workspace-github-account` (от `main`)
**Эпик:** [#62](https://github.com/followLemmi/cowork-deck/issues/62) — подзадачи #49–#61.
**Контекст:** воркспейс сейчас — это `{id, name, path, color}` (`src-tauri/src/model.rs:14`). GitHub-интеграции в приложении нет. `PtyManager::spawn` (`src-tauri/src/pty.rs:22`) не трогает окружение — дочерний `claude` наследует env приложения целиком.

Боль: активный аккаунт `gh` — **глобальное** состояние в `~/.config/gh/hosts.yml`. Пользователь с двумя аккаунтами (рабочий и личный) вынужден переключаться `gh auth switch`, и переключение бьёт по всем сессиям сразу. Две сессии на разных аккаунтах одновременно сегодня невозможны.

## Цель

Привязать GitHub-аккаунт и git-идентичность к воркспейсу так, чтобы сессия рождалась уже с нужным доступом — без переключений, без обращения к глобальному состоянию и без влияния на соседние сессии на других аккаунтах. Показ PR и issues — уже не здесь: эта территория принадлежит эпику [#48](https://github.com/followLemmi/cowork-deck/issues/48), и наш вклад в неё — не свой экран, а готовый резолв токена, на который встанет будущий GitHub-провайдер.

**Ключевая идея:** в системе нет операции «переключить аккаунт». Есть только «у этого процесса такое окружение с рождения». Два процесса с разным env — норма ОС, конфликтовать нечему.

## Границы (scope)

**Входит:** (1) поле `github` у воркспейса, (2) модуль `gh.rs` — детект `gh`, список аккаунтов, резолв токена, (3) инжект env в `PtyManager::spawn`, (4) экран «GitHub» — статус, аккаунты, установка `gh`, добавление аккаунта, (5) поля в форме воркспейса, (6) индикация аккаунта и рассинхрона.

**НЕ входит (YAGNI / позже):**
- **показ PR и issues в UI** — вынесено целиком, см. «Что дальше»: эта территория уже занята эпиком [#48](https://github.com/followLemmi/cowork-deck/issues/48);
- действия над PR/issues из приложения (merge, close, comment, review) — это работа сессии, а не деки;
- уведомления о новых PR/issues и любой фоновый опрос GitHub;
- GHES/self-hosted в UI (поле `host` в модели есть, UI работает только с `github.com`);
- несколько аккаунтов на один воркспейс;
- режим `GH_CONFIG_DIR`-профилей как пользовательский выбор (модель данных его не перекрывает, см. «Что дальше»);
- ротация и обновление токенов — этим владеет `gh`;
- GitLab / Bitbucket;
- смена env у **живой** сессии (технически невозможна — env фиксируется при `fork`).

## Глобальные ограничения (наследуются всеми задачами)

- Tauri v2, ядро Rust + ванильный TypeScript + xterm.js. **Только ванильный TS, без фреймворков.**
- Целевой расход памяти < 100 МБ; только лёгкие зависимости. **Новых зависимостей фича не вводит** — весь GitHub-доступ идёт через `gh` как внешний процесс, свой HTTP-клиент и OAuth не пишем.
- Тёмная тема, палитра One Dark, дизайн-токены из `styles.css` (`:root`). Анимации только на `transform`/`opacity` (ADR-008).
- Строки интерфейса — на русском, в существующем стиле.
- Команды тестов неизменны: `npm test` (vitest run), `cargo test --manifest-path src-tauri/Cargo.toml`. База на момент старта — **131 vitest / 29 cargo**, зелёные; `tsc --noEmit` чист.
- Коммиты — Conventional Commits.

## Ключевые решения (согласованы при брейншторме)

1. **`gh` — единственный источник истины по кредам.** Воркспейс хранит только имя аккаунта (`login`), токен резолвится на спавне через `gh auth token` и живёт только в памяти процесса.
2. **Инвариант: в сторе приложения никогда нет токена.** Ни в `workspaces.json`, ни в keychain приложения, ни в логах. Владелец секретов — keyring `gh`.
3. **Инжект env при спавне, не переключение.** Приложение никогда не выполняет `gh auth switch`, не пишет в `~/.config/gh/hosts.yml` и не правит `.gitconfig` — ноль глобальных мутаций.
4. **git-идентичность — тоже env** (`GIT_AUTHOR_*` / `GIT_COMMITTER_*`), никаких записей в конфиг репозитория.
5. **Деградация при сбое резолва:** сессия стартует, но с `GH_CONFIG_DIR`, указывающим на заведомо пустой каталог — `gh` честно скажет «не залогинен» вместо того, чтобы молча уехать на чужой активный аккаунт.
6. **Установка `gh` и `gh auth login` — в обычном тайле-терминале.** Приложение подставляет команду в **редактируемое** поле, пользователь видит вывод и вводит `sudo`-пароль сам. Приложение не выполняет привилегированных команд вслепую и не участвует в device-flow.
7. **Показ PR и issues сюда не входит.** Изначально он был фазой 2 этой же спеки, но эпик [#48](https://github.com/followLemmi/cowork-deck/issues/48) уже вводит доску задач, счётчик у воркспейса в сайдбаре (#43) и порт `TaskProvider`, поверх которого там прямо предусмотрен GitHub-провайдер. Своя панель дала бы второй счётчик в том же сайдбаре и второе место для списков. См. «Что дальше».

## Почему именно так (отвергнутые альтернативы)

| Альтернатива | Почему нет |
|---|---|
| Свой стор токенов (PAT в OS keychain) | Приложение становится хранителем секретов со всей ответственностью — за то, что уже умеет `gh`. Пользователю пришлось бы вручную заводить и продлевать PAT. |
| `GH_CONFIG_DIR`-профиль на воркспейс | Максимальная изоляция, но пользователь логинится отдельно в каждый профиль и дублирует настройки `gh`. Плохой дефолт; оставлен как возможное расширение — поле `host`/`login` его не перекрывает. |
| `gh auth switch` перед стартом сессии | Ровно та боль, которую чиним: глобальная мутация, гонки между одновременными стартами, поломка соседей. |
| Свой HTTP-клиент к GitHub API + OAuth | Новая зависимость, свой OAuth-flow, своё хранение токенов. `gh` уже установлен у целевого пользователя и всё это умеет. |
| Своя панель PR/issues в этой спеке | Дублировала бы счётчик в сайдбаре и доску из эпика #48. Правильное место — GitHub-провайдер для `TaskProvider`, отдельной спекой после мержа трекера. |

## Проверенные факты о `gh` (v2.82.1)

Всё ниже проверено на машине разработки; на этих свойствах стоит дизайн.

- `GH_TOKEN` / `GITHUB_TOKEN` действуют **только** на `github.com` и поддомены `ghe.com`; для GitHub Enterprise Server у `gh` отдельные `GH_ENTERPRISE_TOKEN` / `GITHUB_ENTERPRISE_TOKEN`. Инжект не задевает Enterprise-хосты.
- `gh auth token --hostname H --user L` отдаёт токен **неактивного** аккаунта — переключение не требуется.
- `gh auth status --json hosts` отдаёт машиночитаемый список: `{state, active, host, login, tokenSource, scopes, gitProtocol}`. Текст парсить не нужно; токены без `--show-token` не светятся.
- При выставленном `GH_TOKEN` сам `gh` **отказывается** делать `auth switch` («The value of the GH_TOKEN environment variable is being used for authentication»). То есть изоляция ещё и принудительная: сессия не может испортить состояние соседей, даже если попытается.
- Git-credential-helper `!gh auth git-credential` (уже прописан глобально `gh auth setup-git`) читает `GH_TOKEN` из окружения **своего** процесса — значит `git push` по https из сессии уходит под аккаунтом воркспейса бесплатно, без нашего участия.

## Модель данных

### Конфиг воркспейса (`workspaces.json`)

```ts
interface WorkspaceGithub {
  host: string;             // "github.com" — единственное значение в UI
  login: string;            // "followLemmi"
  gitName?: string;         // пусто = не инжектим, наследуется из ~/.gitconfig
  gitEmail?: string;
  sshKey?: string;          // путь к приватному ключу для ssh-ремоутов
}

interface Workspace {
  id: string; name: string; path: string; color: string;
  github?: WorkspaceGithub | null;   // отсутствует у старых записей → без привязки
}
```

Rust-зеркало в `model.rs` — с `#[serde(default, skip_serializing_if = "Option::is_none")]`, тем же приёмом, что `Skill.schedule` (`model.rs:32`): старые `workspaces.json` читаются без миграции и не меняют форму на диске.

**Секретов в этой структуре нет и не будет.** `login` — публичное имя.

### Рантайм (нигде не персистится)

```ts
interface GhAccount { host: string; login: string; active: boolean; scopes: string[]; state: string; }
interface GhStatus  { path: string | null; version: string | null; accounts: GhAccount[]; }
```

## Контракт окружения

`gh::session_env(cfg: &WorkspaceGithub, token: Option<&str>) -> Vec<(String, String)>` — **чистая функция**, единственное место, где решается «какие переменные и в каком виде».

**Токен резолвился:**

| Переменная | Значение | Зачем |
|---|---|---|
| `GH_TOKEN` | токен | `gh pr/issue/api` в сессии сразу под нужным аккаунтом; и `git push` по https через credential-helper |
| `GITHUB_PERSONAL_ACCESS_TOKEN` | токен | github MCP-сервер, если сессия его поднимает, наследует env родителя |
| `GIT_AUTHOR_NAME`, `GIT_COMMITTER_NAME` | `cfg.gitName` | авторство коммитов принадлежит воркспейсу |
| `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_EMAIL` | `cfg.gitEmail` | там же |
| `GIT_SSH_COMMAND` | `ssh -i <sshKey> -o IdentitiesOnly=yes` | ssh-ремоуты берут ключ воркспейса |
| `GH_HOST` | `cfg.host` | только если `host != "github.com"` |

Пустые опциональные поля переменных не порождают вовсе — наследование из `~/.gitconfig` остаётся рабочим дефолтом.

**Токен не резолвился (деградация):**

| Переменная | Значение |
|---|---|
| `GH_CONFIG_DIR` | путь к заведомо пустому каталогу `<app_data>/gh-noauth/` |
| `GIT_AUTHOR_*` / `GIT_COMMITTER_*` | как обычно — они известны и без токена |

`GH_TOKEN` при этом **не выставляется**. `gh` в такой сессии сообщит «ты не залогинен, сделай `gh auth login`» — понятная ошибка вместо тихой подмены личности или загадочного 401. Каталог создаётся один раз на запуск приложения и переиспользуется; то, что `gh` положит туда свой `config.yml`, безвредно.

**Воркспейс без `github`:** env пустой, поведение ровно как сегодня.

## Компоненты

### `src-tauri/src/gh.rs` (новый)

Единственное место в коде, знающее о существовании `gh`.

- `which_gh() -> Option<String>` — зеркало `which_claude()` (`commands.rs:89`): override через `COWORK_GH_PATH`, иначе проба `gh --version` на `PATH`.
- `status() -> GhStatus` — `which_gh()` + `gh --version` + `gh auth status --json hosts`.
- `token(host, login) -> Result<String, GhError>` — `gh auth token --hostname H --user L`, **с таймаутом ~5 с**. Залоченный keyring на Linux умеет подвешивать процесс диалогом; без таймаута старт сессии однажды повиснет намертво.
- `session_env(cfg, token) -> Vec<(String, String)>` — чистая, тестируется без `gh` и без сети.

Токен нигде не логируется. Ошибки `gh` перед отдачей во фронт проходят через редактирование на случай, если `gh` вернёт токен в тексте ошибки.

### `src-tauri/src/pty.rs`

`spawn` получает параметр `env: &[(String, String)]` → `cmd.env(k, v)` в цикле. Правка механическая; существующие вызовы передают пустой срез.

### `src-tauri/src/commands.rs`

- `start_session` — перед спавном: воркспейс → `github` → `gh::token` → `gh::session_env`; результат уходит в `spawn`. Исход резолва (успех / деградация + причина) возвращается фронту, чтобы тот показал бейдж.
- Новые команды: `gh_status`, `host_platform` (ОС и, на Linux, дистрибутив из `/etc/os-release`).

Границу проводим так: бэкенд только **сообщает факты об ОС**, а строку команды установки собирает чистая функция во фронте (`installCommand`). Иначе логика, которую надо покрыть тестами по матрице платформ, оказалась бы размазана по двум языкам.

### `src/github.ts` (новый) — чистые функции

- `installCommand(platform, distro) -> string` — `brew install gh` / `winget install --id GitHub.cli` / команда пакетного менеджера Linux; результат идёт в **редактируемое** поле, потому что угадывание пакетного менеджера — гадание.
- `accountLabel(acc)`, `missingScopes(acc)` — предупреждение «у аккаунта нет `repo`, приватные PR не будут видны».

### UI

**Экран «GitHub»** (из палитры команд и пунктом в сайдбаре):
- статус: найден ли `gh`, версия, путь, взят ли он из `COWORK_GH_PATH`;
- `gh` не найден → редактируемое поле с командой установки + кнопка «Установить» (открывает тайл-терминал с этой командой) + ссылка на документацию для тех, кто ставит сам;
- `gh` найден → таблица аккаунтов (логин, хост, активность, скоупы) и «Добавить аккаунт» → тайл с `gh auth login`, device-flow пользователь проходит сам, токен через приложение не проходит;
- кнопка «Перечитать». Скан — при открытии экрана и по кнопке, без фоновых циклов.

**Форма воркспейса** (`src/forms.ts:47`): селект «Аккаунт GitHub» (`— не привязан —` + список; если `gh` нет — строка-заглушка со ссылкой на экран «GitHub»), поля `gitName` / `gitEmail` с плейсхолдером «как в глобальном `.gitconfig`», опционально путь к ssh-ключу, и честная подпись, что изменения подхватят новые и перезапущенные сессии.

**Индикация:** метка аккаунта у строки воркспейса в сайдбаре. Бейдж на тайле — **только** при проблеме: аккаунт не резолвился, или сессия живёт на устаревшем env после смены настройки. В нормальном состоянии тайлы не засоряем.

## Поток данных (старт сессии)

1. Фронт зовёт `start_session` с id воркспейса.
2. Бэкенд читает `Workspace.github`. Нет → пустой env, дальше как сегодня.
3. Есть → `gh::token(host, login)` с таймаутом.
4. Успех → `session_env(cfg, Some(token))`. Сбой → `session_env(cfg, None)` (деградация) + причина.
5. `PtyManager::spawn(..., env)` — `claude` рождается с готовым окружением.
6. Фронт получает исход и, если была деградация, вешает бейдж на тайл.

Токен существует только внутри шага 3–5 и в памяти дочернего процесса. В стор, в лог и во фронт он не попадает.

## Обработка ошибок и крайние случаи

| Ситуация | Поведение |
|---|---|
| `gh` не установлен, воркспейс не привязан | Привязать не к чему; в форме — заглушка со ссылкой на экран «GitHub». Приложение работает как сегодня. |
| `gh` снесли, а привязка осталась | Обычная деградация (пустой `GH_CONFIG_DIR`) + бейдж с причиной «`gh` не найден». |
| `gh` есть, аккаунт вылогинен / удалён из `gh` | Деградация (пустой `GH_CONFIG_DIR`) + бейдж; в форме воркспейса сохранённый `login` помечен «аккаунт не найден в `gh`». |
| Keyring залочен, `gh auth token` висит | Таймаут ~5 с → деградация + бейдж. Старт сессии не блокируется. |
| У аккаунта нет скоупа `repo` | Предупреждение в UI; сессия стартует нормально — публичные репозитории работают. |
| Сменили аккаунт у воркспейса, сессии живут | Живые сессии остаются на старом env (иначе никак — env фиксируется при `fork`). Бейдж «настройка изменилась, нужен перезапуск». |
| Сессия сама делает `gh auth switch` | `gh` откажет из-за выставленного `GH_TOKEN`. Соседи защищены принудительно. |
| Токен утёк бы в лог | Запрещено: перед отдачей во фронт и в лог сообщения `gh` редактируются. |

**Известное ограничение, которое принимаем осознанно:** токен виден в `/proc/<pid>/environ` процессам того же пользователя — ровно как любой `export` в шелле. Это не регресс относительно обычной работы с `gh`.

## Тестирование

**Rust (`cargo test`)** — чистые функции и парсинг фикстур, без запуска `gh` и без сети:
- `session_env` по матрице: нет `github` / есть без идентичности / полный конфиг / с `sshKey` / `host != github.com` / деградация без токена. Проверяем и то, что лишние переменные **не** появляются;
- парсинг `gh auth status --json hosts` на фикстурах: два аккаунта, ноль аккаунтов, `state != success`, отсутствующие поля;
- парсинг `gh pr list --json` / `gh issue list --json` на фикстурах, включая пустой список;
- сериализация `Workspace` с `github` и round-trip старого `workspaces.json` **без** поля (обратная совместимость);
- редактирование токена в сообщениях об ошибках.

**TS (`vitest`)** — чистые функции:
- `installCommand` по платформам и дистрибутивам;
- `missingScopes` и формирование предупреждения;
- состояния селекта аккаунтов (`gh` нет / аккаунтов нет / есть / сохранённый `login` отсутствует в списке);
- валидация формы воркспейса;

Существующие тесты остаются зелёными (**131 vitest / 29 cargo**); `tsc --noEmit` чист.

Ручная проверка, которую автотестами не закрыть: два воркспейса на разных аккаунтах, по сессии в каждом, одновременно — `gh pr list` в обеих отдаёт разные результаты, `git push` уходит от разных лиц, и ни одна не влияет на другую.

Эпик [#48](https://github.com/followLemmi/cowork-deck/issues/48) вводит порт `TaskProvider`, доску на всю ширину и счётчик у воркспейса в сайдбаре, и прямо называет GitHub-провайдер отдельной спекой поверх готового порта. Резолв токена из `gh.rs` закрывает вопрос аутентификации, который там оставлен открытым, — значит правильный порядок такой: сначала эта спека, потом мерж трекера, потом провайдер. Готовые к переносу решения: скоуп «репозиторий воркспейса», read-only, обновление по требованию без фонового опроса, кеш с TTL, отдача кеша с пометкой возраста при ошибке или рейт-лимите.
- Режим `GH_CONFIG_DIR`-профилей для тех, кому нужен полноценный изолированный `gh` внутри сессии (GHES, экзотика). Модель данных готова: добавляется опциональное поле, `session_env` получает вторую ветку.
- GHES / self-hosted в UI — поле `host` уже есть, нужен только выбор хоста и `GH_ENTERPRISE_TOKEN` в контракте env.
- Действия над PR/issues из деки — сознательно оставлены сессии.
