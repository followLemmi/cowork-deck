# cowork-deck — «Прогнать запланированный сценарий сейчас» — Design Spec

**Дата:** 2026-07-26
**Ветка:** feat/scheduled-scenarios (продолжение #9)
**Контекст:** запланированные сценарии (#9) реализованы: бэкенд-планировщик решает «когда» и эмитит `schedule://fire`, фронт исполняет через `handleScheduledFire` → `Deck.launchScheduled` (дефолты плейсхолдеров, ⏰-плитка, guard наложения). Ручной запуск сценария кликом по его кнопке существует давно, но идёт другим путём: спрашивает плейсхолдеры и открывает плитку в **активном** пространстве.

## Цель
Дать кнопку «прогнать сейчас» у сценария с включённым расписанием: тот же прогон, что сделало бы расписание, но по требованию — чтобы проверить сценарий, не подводя часы, или прогнать его внеочередно.

## Границы (scope)
**Входит:** кнопка в строке сценария, переиспользование существующего пути срабатывания, обратная связь при отказе, вынос правил выбора пространства в чистую функцию.

**НЕ входит:** изменения в Rust; «прогнать сейчас» у сценариев без расписания (обычный ручной запуск уже есть); история прогонов; пункт в командной палитре.

## Ключевые решения
1. **Ручной прогон не влияет на расписание.** `lastRun` не трогаем — в 08:50 нажатый прогон не отменяет срабатывание в 09:00. Гарантируется структурно: `schedule_state.json` пишет только цикл планировщика в Rust, а фича целиком фронтовая.
2. **Один путь с плановым прогоном.** Кнопка зовёт тот же `handleScheduledFire(skillId)`, что и событие из бэкенда: дефолты вместо вопросов, заголовок `⏰ icon name`, guard наложения. Никакой второй реализации срабатывания.
3. **Кнопка вместо индикатора.** ⏰ из кнопки сценария переезжает в отдельную кнопку `.sk-now` рядом с ✎/✕ — она и индикатор расписания (тултип с правилом и следующим запуском), и действие. Двух ⏰ в строке нет. Побочно уходит нынешняя странность: клик по ⏰ внутри кнопки сценария запускал обычный ручной запуск.
4. **Отказ виден.** Клик, не приведший к прогону, показывает `alertModal` — в отличие от планового прогона, где отказ уходит в консоль.

## Компоненты

### `src/schedule.ts` (правка) — правила выбора пространства
Новая чистая функция, снимающая логику с `main.ts`:

```ts
type WorkspaceResolution =
  | { ok: true; workspace: Workspace }
  | { ok: false; reason: "no-workspace" };

resolveScheduledWorkspace(skill: Skill, all: Workspace[], active: Workspace | null): WorkspaceResolution
```
Правила (те же, что уже действуют для планового прогона):
- `skill.workspaceId` задан и такое пространство есть → оно;
- `skill.workspaceId` не задан (сценарий не привязан) → активное;
- `skill.workspaceId` задан, но пространство удалено → `no-workspace` (не запускаем в чужой папке);
- привязки нет и активного пространства нет → `no-workspace`.

### `src/main.ts` (правка) — статус вместо молчания
`handleScheduledFire(skillId)` начинает возвращать статус:

```ts
type FireOutcome = "launched" | "skipped-overlap" | "no-workspace" | "not-scheduled";
```
- слушатель `schedule://fire` статус игнорирует (как сейчас — лог при отказе);
- кнопка ждёт статус и при `!== "launched"` показывает `alertModal`:
  - `skipped-overlap` → «Прогон пропущен: предыдущий ещё активен.»
  - `no-workspace` → «У сценария нет доступного пространства: привяжите его или выберите пространство.»
  - `not-scheduled` → сообщения нет (кнопка существует только у запланированных; ветка недостижима из UI).

### `src/skills.ts` (правка) — кнопка в строке
- Конструктор `SkillsPanel` получает четвёртый колбэк `onRunScheduled: (skill: Skill) => void`.
- В `render()` для `s.schedule?.enabled`: кнопка `.sk-now`, текст `⏰`, `title` = `прогнать сейчас · ${describeSchedule(s.schedule)} · след.: ${nextRunLabel(s.schedule.preset, new Date())}`, `onclick` → `onRunScheduled(s)`.
- Существующий `span.sk-sched` внутри кнопки сценария удаляется (заменён кнопкой).
- Порядок в строке: `[▶ имя] [⏰] [✎] [✕]`.

### `src/styles.css` (правка)
`.sk-now` — по образцу `.sk-edit`/`.sk-del` (те же размеры и hover), `.sk-sched` удаляется.

## Поток данных
```
клик .sk-now ──▶ onRunScheduled(skill) ──▶ handleScheduledFire(skill.id)
                                              ├─ resolveScheduledWorkspace
                                              ├─ fillPlaceholders(prompt, schedule.defaults)
                                              └─ Deck.launchScheduled (guard наложения)
                                                   └─ spawnTile → start_session
   отказ ◀── статус ── alertModal

цикл планировщика (Rust) ──▶ "schedule://fire" ──▶ тот же handleScheduledFire (статус → лог)
```
`schedule_state.json` в этом потоке не участвует.

## Крайние случаи
| Случай | Поведение |
|---|---|
| Предыдущий прогон этого сценария активен (`working`/`waitingInput`) | прогон не запускается, `alertModal` «предыдущий ещё активен» |
| Сценарий привязан к удалённому пространству | прогон не запускается, `alertModal` про пространство |
| Сценарий не привязан, активного пространства нет | то же сообщение |
| Расписание выключено | кнопки нет в строке |
| Нажали в 08:50 при «ежедневно 09:00» | прогон идёт; в 09:00 плановый прогон тоже идёт (если тот уже завершён — guard не мешает) |
| `claude` не найден | плитка → `ошибка`, существующий путь |

## Тестирование
**vitest:**
- `resolveScheduledWorkspace` — все четыре правила (привязка есть, привязки нет, привязка битая, активного нет);
- `skills.test.ts` — ⏰-кнопка есть только у запланированного сценария; клик зовёт `onRunScheduled` с этим сценарием и **не** зовёт `onLaunch`; тултип содержит правило и «след.:»; `.sk-sched` больше не рендерится.

**Ручная приёмка (GUI):** клик ⏰ прогоняет сценарий вне расписания (заголовок `⏰ …`, дефолты подставлены); повторный клик при активном прогоне даёт модалку; после ручного прогона плановое время всё равно срабатывает.

**Регресс:** обычный ручной запуск (клик по имени) по-прежнему спрашивает плейсхолдеры и идёт в активное пространство.
